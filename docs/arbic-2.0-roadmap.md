# خارطة طريق Arbic 2.0

> **آخر تحديث:** 2026-11-08
> **الأساس:** نتائج Phase 0 في `docs/architecture-audit.md` و`docs/current-feature-status.md` و`docs/technical-debt.md`.
> **القاعدة الحاكمة:** كل مرحلة تُغلق ببوابة قبول مختبَرة قبل بدء التالية. لا يُنفَّذ أكثر من مرحلة في تغيير واحد غير مراجع.

---

## 1. مبادئ التنفيذ

1. **الحفاظ على الموجود:** لا إعادة كتابة شاملة. كل توسعة تُبنى على `Lexer`/`Parser`/`AST`/`Interpreter` الحالية.
2. **الدليل قبل الادعاء:** لا تُصنَّف ميزة مكتملة بلا: تنفيذ + اختبارات وحدة + تكامل + رجعية + توثيق + مثال + معالجة أخطاء.
3. **عقد ثابت:** `errors.py` و`pyproject.toml` وواجهات الطبقات هي العقود؛ التوثيق يُفحص ضدها.
4. **التوافق أولًا:** برامج `.arb` التي تعمل اليوم يجب أن تظل تعمل. أي كسر يحتاج ADR + دليل ترحيل + اختبار توافق.
5. **الأمان ليس خيارًا لاحقًا:** أي تنفيذ كود غير موثوق (interop/playground/packages) يتطلب عزلًا خارج العملية قبل كتابة الميزة.
6. **لا GC مخصص ولا تحسين بلا قياس.**

---

## 2. لماذا أُعيد ترتيب المراحل؟

الماستر برومبت يضع OOP قبل نظام الأنواع وقبل الدوال ضمنيًا. الواقع يقول: **لا توجد دوال أصلًا.** لذا:

- OOP بلا دوال = مستحيل.
- Generics/Union types بلا semantic analyzer = مستحيل.
- IR بلا AST كامل (دوال/مجموعات/وحدات) = IR فقير لا يمثل البرامج الحقيقية.
- VM بلا IR = ستُعيد كتابة الـ AST-to-bytecode مرتين.
- Stdlib بلا `استورد` ودوال = مجموعة دوال مدمجة فقط، لا مكتبة.

الترتيب التالي يعكس التبعيات الفعلية، مع الإبقاء على أسماء مراحل الماستر حيث أمكن.

## 4. تفصيل المراحل

### Phase 0 — تدقيق المستودع ✅

**المنجز:** انظر `docs/architecture-audit.md` §12.
**المخرج:** 4 مستندات + تقرير تطوير، بلا تغيير كود.
**البوابة:** لا تغييرات تدميرية؛ كل ادعاء مسنود لكود/تشغيل. ✅

---

### Phase 1 — تثبيت الأساس والأمان

**الأهداف:**
1. إزالة/تأمين ملفات الاعتماد (TD-01) وإضافة سياسة أمان.
2. CI على Python 3.12/3.13: ruff + mypy + pytest (TD-04).
3. تصحيح كل انحرافات التوثيق المسجلة (TD-02، TD-03، TD-05) أو تنفيذ السلوك الموعود.
4. تثبيت عقد أكواد الخروج (`0/1/2`) في المواصفة واختباره.
5. معالجة `كرر` بقيم سالبة/كسرية بقرار موثّق (TD-10).
6. تحصين REPL heuristic باختبارات حدّية (TD-11).
7. إضافة fuzz خفيف للـ lexer/parser وproperty tests أساسية (TD-14).
8. harness قياسات أداء أولي (TD-15).
9. توثيق سياسة الإصدارات والتوافق (ADR-01، TD-21).
10. إزالة `type: ignore` من CLI وتوحيد قراءة المصدر (TD-16).

**المخرج:** CI أخضر، docs مطابقة، `SECURITY.md`، `CONTRIBUTING.md`، baseline benchmarks، اختبارات انحدار موسّعة.

**البوابة:**
- `pytest` + `ruff` + `mypy` خضراء في CI على إصدارَي Python.
- لا ادعاء في `syntax.md`/`README.md` يخالف السلوك (اختبار توثيق آلي أو مراجعة موثقة).
- ملفات الاعتماد إما محذوفة أو مؤمّنة وموثّق ذلك.
- `git status` نظيف من الأسرار.

**غير مشمول:** أي ميزة لغوية جديدة.

---

### Phase 2 — اللغة 2.0: دوال، مجموعات، وحدات

**الأهداف:**
1. **دوال:** `دالة اسم(وسائط) -> نوع:`، `رجّع`، استدعاء، arity، نطاق محلي، أخطاء واضحة.
2. **مجموعات:** `قائمة`، `قاموس`، أدبيات `[1, 2]` و`{"م": 1}`، فهرسة، إسناد عنصر، طول، تكرار.
3. **وحدات:** `استورد`، مسارات آمنة، منع traversal، دورة استيراد، أسماء مؤهلة.
4. **تحسينات صياغة:** تعبير متعدد الأسطر داخل الأقواس (TD-03)، `غير كده لو`، `break`/`continue`، `const`.
5. **تحديث AST/Interpreter/CLI** دون كسر البرامج القائمة.

**المخرج:** مواصفة نحوية رسمية للدوال/المجموعات/الوحدات، AST nodes، تنفيذ، اختبارات، أمثلة، توثيق.

**البوابة:**
- 100% من برامج Phase 0 الرجعية ما زالت تعمل حرفيًا.
- اختبارات parser للقواعد الجديدة + اختبارات runtime + حالات خطأ.
- `arabic check` يكشف أخطاء الدوال/الاستدعاء قبل التشغيل (حتى لو ديناميكيًا).
- قرار ADR-02 (نطاق الكتل) مطبّق ومختبَر.

**تنبيه:** هذه أكبر مرحلة لغوية؛ تُقسَّم إلى PRs صغيرة: دوال ← مجموعات ← وحدات ← صياغة.

---

### Phase 3 — OOP والبرمجة التعبيرية

**الأهداف:** `صنف`، `__تهيئة__`، خصائص، وراثة، تغليف، طرق ساكنة، protocols/interfaces، lambda، دوال عالية الرتبة، decorators حيث لها مبرر، pattern matching تدريجيًا، context managers، generators.

**البوابة:**
- دلالات واضحة للوراثة المتعددة (أو منعها صراحة).
- اختبارات لكل ميزة + توثيق + أمثلة.
- لا تعارض مع `Environment`/الاستدعاءات من Phase 2.

---

### Phase 4 — التحليل الدلالي ونظام الأنواع 1.0

**الأهداف:**
1. Symbol tables ونطاقات وmodule-aware analysis.
2. Type checker تدريجي: `عدد`، `عشري`، `نص`، `منطقي`، `فراغ`، `أي`، `قائمة[T]`، `قاموس[K,V]`، `اختياري[T]`، union types.
3. Annotations، استدلال محلي، strict mode.
4. تشخيصات نوعية بأكواد جديدة + اختبارات سالبة.
5. تعريف دلالة `أي` صراحة.

**البوابة:**
- كل عملية نوعية غير صالحة لها اختبار سلبي.
- `arabic check` يكتشف أخطاء الأنواع قبل التشغيل في الوضع الصارم.
- التوثيق يوضح الفرق بين الوضع المرن/الصارم.

---

### Phase 5 — IR والمحسِّن

**الأهداف:** تصميم IR مستقل (SSA أو ثلاثي العناوين — قرار موثّق)، AST→IR lowering، تحقق من الـ IR، ثوابت folding، dead code elimination، constant propagation، CSE عند الحاجة، أدوات فحص IR.

**البوابة:**
- تنفيذ مفسّر IR يعطي نفس مخرجات المفسّر الشجري لكل برامج الرجعية (differential tests).
- كل optimization له اختبار «قبل/بعد» يثبت تطابق الدلالة.
- لا ادعاء تحسين أداء بلا قياس.

---

### Phase 6 — Runtime هجين 2.0 وVM

**الأهداف:**
1. Bytecode بصيغة مُصدَّرة (magic + version + checksums).
2. تعليمات: متغيرات، حسابات، قفزات، استدعاءات، مجموعات، استثناءات، وحدات.
3. Stack VM (أو register وفق ADR-05) مع source maps وdebug info.
4. Bytecode validation قبل التنفيذ.
5. اختيار محرك التنفيذ (`--engine=interpreter|vm`).
6. Python interop: allowlist، تحويلات أنواع صريحة، أخطاء Python، **عزل خارج العملية للكود غير الموثوق**.

**البوابة:**
- اختبارات تفاضلية: Interpreter vs VM متطابقة على كل الميزات المشتركة.
- VM يرفض bytecode تالف/معدّل.
- interop لا يمنح وصولًا غير مقصود لبايثون الداخلية، والعزل موثّق بحدوده.

---

### Phase 7 — المكتبة القياسية 1.0

**الأهداف:** `مكتبة.رياضيات`، `نصوص`، `قوائم`، `ملفات`، `وقت`، `عشوائي`، `JSON`، `نظام`، `أخطاء`، `اختبارات`.

**متطلبات كل وحدة:** API عربي متسق، توثيق، أمثلة، اختبارات، تحقق مدخلات، أخطاء واضحة، سياسة توافق.

**البوابة:** لا وحدة تُنشر بلا واجهة موثّقة واختبارات؛ سلوك مستقل عن تفاصيل بايثون الداخلية.

---

### Phase 8 — مدير الحزم وCLI

**الأهداف:** `init`، `build`، `check`، `test`، `format`، `install`، `remove`، `update`، `search`، `publish`، `list`، `doctor`، `repl`. نظام حزم بـ SemVer، lockfile، checksums، resolver بالتراجع، استخراج آمن.

**البوابة الأمنية (إلزامية):** اختبارات تثبت رفض:
- `../` path traversal،
- المسارات المطلقة،
- symlink escape،
- archive bombs بحدود،
- dependency confusion،
- سكربتات تثبيت غير موقعة/غير مصرّح بها.

---

### Phase 9 — أدوات المطوّر

**الأهداف:** formatter حتمي (idempotent)، LSP (تشخيصات، إكمال، hover، تعريف، مراجع، rename، symbols، signature help، code actions)، VS Code extension، debugger متوافق DAP (breakpoints/step/stack/variables) للمفسّر والـ VM.

**البوابة:** formatter يعطي نفس الناتج عند التطبيق مرتين؛ LSP يستهلك نفس `DiagnosticBag`؛ debugger يعمل على المحركين.

---

### Phase 10 — Playground والإصدار 2.0

**الأهداف:** playground معزول بحدود موارد، توثيق كامل (مواصفة، ترحيل، أمان، معمارية)، fuzz/property/security suites، benchmarks نهائية، حزمة إصدار 2.0.

**البوابة:** لا تنفيذ كود مستخدم على الخادم بلا عزل؛ كل مستندات `docs/` موجودة ومطابقة؛ الإصدار يحمل changelog وترحيلًا.

1. برامج `.arb` الصحيحة في 0.1 تظل صحيحة في 2.0، إلا ما يُعلن كسرُه في ADR + `migration-2.0.md`.

4. أكواد الأخطاء القائمة لا تُعاد استخدامها بمعنى مختلف؛ الجديد بأرقام جديدة.
5. مخرجات `legacy/masry.py` تبقى المرجع الرجعي حتى إعلان إيقافها.
