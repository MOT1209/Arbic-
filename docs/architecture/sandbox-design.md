# تصميم عزل التنفيذ (Sandbox) — وثيقة تصميم

- **الحالة:** تصميم + تنفيذ (`al_arabiya/sandbox/`): حدود موارد على كل الأنظمة، وحجب شبكة/كتابة بـ seccomp على Linux x86_64
- **البند المرتبط:** TD-20
- **القاعدة:** أي ميزة بتشغّل كودًا غير موثوق (playground، interop، تنفيذ حزم
  من سجلّ خارجي) **ممنوع** تتشحن قبل تنفيذ النموذج ده واختباره.

## ليه

النهارده البرامج بتشتغل بنفس صلاحيات المستخدم: تقدر تقرأ/تكتب أي ملف، وتفتح
شبكة، وتستهلك وقتًا/ذاكرة بلا حد (غير حارس الـ 1,000,000 لفة). ده مقبول
لبرنامج محلي بيشغّله صاحبه، ومرفوض لأي كود جاي من مكان تاني.

## نموذج التهديد

| التهديد | المطلوب منعًا |
|---|---|
| قراءة ملفات برّه المشروع | رؤية مجلد المشروع فقط، للقراءة |
| الكتابة على القرص | ممنوعة تمامًا (أو مجلد مؤقت في الذاكرة) |
| شبكة | ممنوعة تمامًا |
| استهلاك CPU/RAM | حدود صلبة (time/memory/rlimit) |
| الهروب من العزل | sandbox على مستوى الـ OS + عملية منفصلة |
| تسريب بيانات عبر التشخيصات | رسائل بتشير للمصدر بس، من غير مسارات مطلقة |
| حلقة لا نهائية | حد وقت + حارس الحلقات الموجود |

## المنفّذ فعليًا

| الطبقة | الحالة |
|---|---|
| عملية عاملة منفصلة (`python -m al_arabiya.sandbox.worker`) | ✅ |
| سقف ذاكرة | ✅ `RLIMIT_AS` على POSIX · Job Object على Windows |
| سقف وقت CPU + مهلة حائط | ✅ `RLIMIT_CPU` + قتل العملية عند المهلة |
| منع كتابة الملفات | ✅ `RLIMIT_FSIZE=0` على POSIX (اللغة أصلًا مفيهاش كتابة) |
| سقف مخرجات | ✅ stdout/stderr مقصوصان عند الحد (exit 3) |
| مدخلات | ✅ stdin مقفول — `اقرأ` بترجع «مفيش إدخال متاح» |
| بيئة نظيفة | ✅ `PATH`/`SYSTEMROOT` بس + `PYTHONPATH` والمشروع، بدون أسرار أو سجلّ |
| حجب الشبكة وكتابة الملفات — Linux x86_64 | ✅ seccomp BPF: `socket`/`connect`/`bind`/… و`open`/`openat` للكتابة بـ `EPERM` (القراءة مسموحة) |
| نفس الحجب — Windows / macOS / معماريات أخرى | ⛔ لسه (AppContainer / `sandbox-exec`) — مطلوب قبل interop أو أي I/O |
| sandbox على مستوى الحاويات/الـ namespaces | ⛔ لسه |

## التصميم المقترح

### 1. عملية عاملة (worker) منفصلة

- الـ CLI/الخدمة بتبعت البرنامج + مدخلات stdin عبر pipe، والـ worker بيرجّع
  stdout/stderr/كود الخروج + التشخيصات بصيغة JSON محدودة الحجم.
- ممنوع أي `exec`/`eval` لكود المستخدم داخل عملية الخدمة نفسها.

### 2. قيود على مستوى نظام التشغيل

| النظام | الأداة |
|---|---|
| Linux | namespaces (mount/pid/net/user) + `seccomp` + `setrlimit` (CPU، AS، NOFILE) |
| Windows | Job Object بحدود ذاكرة/وقت + AppContainer بدون شبكة + توكن مقيّد |
| macOS | `sandbox-exec` بملف سياسة يسمح بقراءة المشروع فقط |

### 3. قيود اللغة

- `استورد` جوه العزل بيتقيّد بمجلد المشروع (القاعدة المنفّذة حاليًا).
- الحزم المثبتة لازم تكون **مجردة من الـ symlinks** وبصماتها متطابقة (منفّذ
  في مدير الحزم)؛ السجلّ الخارجي يحتاج توقيعًا فوق ده.
- `قرأ` بيتقفل، أو بيتصرف من مدخلات محددة مسبقًا.

### 4. القياس والمراقبة

- حد وقت حائط لكل تشغيل (مثلًا 2 ثانية للـ playground) + حد ذاكرة (128MB).
- عند تجاوز الحد: إنهاء الـ worker، ورسالة `E4xxx` واضحة، مش traceback.

## اختبارات القبول (قبل الشحن)

1. برنامج بيقرأ ملفًا برّه المشروع → يفشل بـ `E4016` ومفيش محتوى بيتسرّب — ✅ (`tests/modules`).
2. برنامج بيحاول يفتح شبكة → ممنوع على مستوى الـ OS — ✅ Linux x86_64 (`tests/sandbox/test_os_guard.py`)؛ Windows/macOS لسه.
3. برنامج بيكتب ملفًا → ممنوع، والمجلد الأصلي ما اتغيّرش — ✅ على POSIX بـ `RLIMIT_FSIZE=0`، وعلى Linux x86_64 كمان بـ seccomp (الكتابة بترجع `EPERM` حتى لو الحد اتشال).
4. حلقة لا نهائية → ينهي عند الحد الزمني، والخدمة تفضل شغّالة — ✅ (`tests/sandbox`).
5. استهلاك ذاكرة ضخم → الـ worker بيموت، الخدمة سليمة — ✅ (POSIX مختبَر؛ Windows Job Object منفّذ).
6. برنامج سليم → نفس المخرجات بالظبط زي التشغيل المحلي (parity) — ✅.

## اللي **مش** كفاية

- allowlist للدوال المدمجة: بيتخطاها بـ `getattr` أو عبر مكتبة قياسية أوسع.
- تعطيل `import` في Python: البرنامج مش Python أصلًا، لكن الـ worker ممكن
  يستغل أي واجهة interop مستقبلية.
- حدود الحلقات وحدها: مش بتمنع قراءة الملفات ولا الشبكة.
